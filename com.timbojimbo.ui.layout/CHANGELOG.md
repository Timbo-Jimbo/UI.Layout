## [Unreleased]

### Added

- `LayoutNode`: one component per laid-out `RectTransform`, modelled on Clay's layout model. Per-axis `Sizing` (Fit, Grow, Fixed or Percent, with min and max), a layout `Direction`, `Padding` (one Vector4 in left, right, top, bottom order so bindings see four channels), `Gap`, child alignment on both axes (Left/Center/Right and Top/Center/Bottom, plus `SpaceBetween`, which shares the free space out between the children along the flow on top of the gap), `AlignSelf` (a child's own place across its parent's flow: Auto, Start, Center or End), an `AspectRatio` that derives a Fit height from the width (or a Fit width from a Fixed height), and floating placement (`AttachTo` the parent, the root or another node, with an attach point on each side and an offset) that takes the node out of the flow and out of its parent's Fit size; a floating node's Grow and Percent sizes are of its parent's whole rect, padding included, as CSS sizes an absolutely positioned box. A node whose parent object has no enabled node is a root; only roots are laid out, and everything below them is owned by the engine. Every field is a plain serialized value with a dirtying setter
- `LayoutEngine`: the algorithm as a pure pass over the tree. Content is measured unconstrained, Fit sizes accumulate bottom-up, each axis is sized top-down (Percent of the inner size minus gaps, Grow shares the remaining space smallest-first up to each max, on overflow Grow and Fit children shrink largest-first down to their minimum), content is measured again at its final width so text wraps before the vertical pass, then flow positions and alignment are resolved, and floating nodes are placed against their targets. Nothing touches a `RectTransform` until the commit, which writes anchors, size and position once and tracks them as driven properties, so a loaded scene starts with its nodes unsized and is laid out before its first render. Layout state is kept on the node (`LayoutRect`) rather than read back from the transform
- `Insets.All`, `Insets.Symmetric` and `Insets.Of(left, right, top, bottom)` build padding so a call site reads as what it means, and the inspector labels the padding's sides L, R, T and B
- An `AttachTo.Element` target that is not a node of the same tree floats against the parent instead, with a warning (once per node and target) in the editor and development builds
- `LayoutNode.Offset`: a translation composed at commit that never affects siblings or the parent and never runs a pass; setting it moves the node in place, so it is the field to animate
- `LayoutTransition`: a delay, a duration and an `EaseType`, after CSS animation-delay, animation-duration and animation-timing-function; `LayoutTransition.Instant` (no duration, no delay) applies at once. `Motion` (`.With(motion)`) says how a move travels: an `ITransitionMotion` is a pure function, given where the thing starts and ends and how far along it is, returning a `MotionFrame`: its centre, size, a visual scale around the centre, an opacity, and its `Morph`, how far its contents have gone from the old state to the new (0 to 1): a matched pair's halves blend by it, and what rides inside (parts flying inside a flying container, nodes moving inside a moving parent) goes from its old place and size to its new ones by it. Following the eased progress it is a cross-fade with the parts gliding into place; held and then jumped while nothing shows, the contents keep their old arrangement until the swap. The engine is the only thing that writes to the objects, and it takes the look off when the move ends, however it ends. None is a straight line morphing on the eased progress. `ArcMotion` (`.Curved(c)`) is the built-in one: a smooth arc (a quadratic Bézier whose control point slides with its curvature from the midpoint towards the corner of the L that takes the shorter axis first) that sets off along the shorter axis and arrives along the longer one. Only what moves as a whole follows a motion: a node moving inside a moving parent goes straight within it, and a part flying inside a flying container rides the container, its path, scale, opacity and morph. A node's own motion is a serialized reference beside its transition, picked in the inspector from every motion type in the project. `LayoutNode.Transition` (a `LayoutTransition?`) is the node's override inside a view transition, the way a CSS rule on `::view-transition-group(name)` overrides the default: null inherits the transition's timing, and `Instant` makes the node snap while everything around it animates. The inspector shows it as Inherit or Custom with its timing on one line. Outside a view transition layout is instant. `LayoutRect` is the target; `VisualRect` and `IsTransitioning` say where a node is on the way. Moves tick in the same pre-render hook as layout, after the dirty trees
- View transitions, after the web API. `LayoutSystem.StartViewTransition(update, transition, types)` captures where every enabled node is shown (in world space, so a node is matched across parents and trees), runs the update, lays the new state out, and animates the difference as one transition, returning a `ViewTransition` with `Finished` and `SkipTransition()`. The difference is sorted into groups the way the web sorts captured elements: movers (a node shown somewhere else travels there in place, from where it was; one that only rode its parent does nothing), named pairs, persisting pairs, exits and the topmost entering nodes. No snapshots are taken: the objects themselves move, so anything animating on them keeps going. Nodes move with the given transition (default `ViewTransition.DefaultTransition`, a quarter second easing out) unless they set their own; `Instant` applies the update at once. `types` say what kind of change it is ("forward", "back"), like the web's view transition types, for animators to read through `ViewTransition.HasType`; `ViewTransition.Transition` and `TransitionFor(node)` give them the timing. A layout pass during a transition leaves the moves alone, and a changed target retargets a moving node with the move's own timing. A root's own rect never animates, since it is what a ScrollRect or a UGUI parent reads. A transition started inside another's update joins it (no layout of its own, the outer timing and types), so an item that dismisses itself with its own transition can be cleared with the others from a bigger one. A transition started over the same nodes takes over the one in flight, which finishes: its moves go on from where they are under the new one (a move the new update changes restarts from where it is drawn, with the new timing), fades go on from the alpha they have reached, enter and exit effects play on with the new transition waiting for them, and only its lifted flights land. `SkipTransition()` ends a transition at once, effects included, and a duplicate name skips the transition with a warning, as on the web. Deactivating a node inside the update makes it vanish at once, since a disabled object cannot be drawn; in the editor a warning names it and points to `Exit`.
- Scoped view transitions, like the web's `element.startViewTransition`: `LayoutSystem.StartViewTransition(scope, update, transition, types)` captures and animates only the subtree under `scope` (any component; its own node never moves) and matches names within it, so transitions in separate parts of the UI run side by side; only one whose subtree overlaps (contains or is contained by) takes over. Changes the update makes outside the scope apply at once, and in the editor a warning names a node outside it that moved. The unscoped call is the whole UI Moves advance with the unscaled clock unless `LayoutSystem.UseScaledTime` is set, in which case they slow and pause with `Time.timeScale`. `LayoutSystem.DeltaTime` is that step, for enter and exit animators to follow; `ViewTransitionSequences` ticks its sequences with it
- The transition layer: named pairs, persisting pairs and carried nodes are lifted out of their trees into a plain rect kept as the last child of their canvas, a placeholder of the same size (and the same flow state) keeping each one's layout slot, and stacked there in capture order as the web's groups are in its top layer, so what draws over what no longer depends on the trees. Each flies a straight line from its captured rect to its slot, read live, so a scroll or a reflow during the transition is honoured; a lifted container keeps the layout its content was given for its final size. Enters and exits fade or play their animator in place beneath the layer (a leaving one lets clicks through). Nothing is left on an object afterwards but the fade's CanvasGroup
- `IViewTransitionAnimator`: how a node looks while it enters or leaves, the way keyframes on the web's old and new pseudo-elements do. The engine calls `Enter` on a node's first layout inside a transition, and outside one when the node arrives (its first layout under a node that was already shown, with a null transition; a scene's first layout arrives nowhere), and `Exit` when `LayoutSystem.Exit` takes it out, each with a `done` the transition's `Finished` waits for and that lets a leaving node go, and `Skip` when the transition is skipped or the node is called back. Only the topmost new node of a subtree enters, the rest rides with it. `LayoutSystem.Settle(root)` opens a scope in which nodes enabled below `root` just appear instead of entering, for content that was already there as far as the player is concerned. `ViewTransitionSequences`, present while the Sequencer package is installed (optional reference, `TJ_LAYOUT_SEQUENCER`), implements it with authored sequences: an enter and an exit, and per-type rules that pick others for transitions of a given type. Without an animator an entering or leaving subtree fades through a CanvasGroup, added the first time the object needs one and left in place; fades follow the move's own ease
- `LayoutSystem.Exit(node, onExited)`: takes a node out, the tree reflowing without it at its next pass while the node, still enabled, plays its exit effect (its animator's, or a fade with the running view transition's timing; outside one a node without an animator leaves at once); then the object is deactivated and the callback runs, so a page spawned for a transition can be destroyed on the way back. A delayed transition makes the siblings wait for the exit before closing up. `LayoutNode.IsExiting` says which state a node is in. `LayoutSystem.Show(node)` activates a node, or calls one that is leaving back: the exit is cancelled (its animator told to skip, its callback never run) and, inside a view transition, the node enters again from wherever its exit had got to. `LayoutNode.Shown` reads active-and-staying and writes `Show` or `Exit`
- `LayoutSystem.Hide(node)`: hides a node in its place, like CSS `visibility: hidden` beside `Exit`'s `display: none`. The tree goes on laying it out, but it is not drawn and takes no clicks, and to view transitions it is gone, its names with it: inside one it fades out where it is, or, as the old half of a pair, flies into the node that took its name and waits in its slot unseen. `Show` brings it back, so a node leaving with the name lands onto it. An old half that stays in the page does not fly; the new one grows out of it.
- `LayoutNode.ViewTransitionName`, the web's `view-transition-name`, and `ViewTransitionScope`, which namespaces the names below a node (`scope/name`): part names are authored in a prefab and the scope is set to the item's id on the instance's root when it is bound, so a list of one prefab has no duplicates and a page given the same scope pairs with that instance's parts. A name found in only one state rides whatever its tree does
- `LayoutNode.ViewTransitionPersist`, after Astro's `transition:persist`: a pair with the flag is not cross-faded; the kept object flies into the new spot with its state intact, its content laid out against its rect as it goes, and when the transition ends the two swap places, the copy taking the old slot or going with the old tree if that tree is gone. Flagging one copy is enough, since the flag travels with the kept object. A persisting object keeps its own sizing, so it is sized by a slot node on each side. A flagged node the update moves to a new parent is carried there: lifted and flown from its old slot to its new one, the same object throughout with no copy and no swap, which is how a live object (a playing video) is handed to another screen. A persisting background as an earlier sibling of a named body grounds a page transition: the surface itself grows from the card into the page while the bodies cross-fade over it
- `ILayoutMeasurable.SizeIsAnimatable` (default false): content that can be drawn between two sizes lets a transition animate the node's size; text keeps the position-only rule. UGUI content answers true for an Image, a RawImage or a bare LayoutElement and false for a graphic that measures itself (a text)
- `ILayoutMeasurable`: the leaf contract (`Measure(availableWidth)` and `MinWidth`), so content answers "how tall at this width" as a pure function
- UGUI compatibility inside `LayoutNode`: a leaf with no `ILayoutMeasurable` but with UGUI `ILayoutElement`s (LayoutElement, Image, TextMeshPro) measures them the way a UGUI group would, and every Graphic's dirty-layout callback marks the node, so a sprite or text change reflows the tree without any adapter component. This is a compromise kept in its own file: `ILayoutElement` only answers for the width on its transform, so the node writes the width it is asked about before reading (the pass then writes the real rect), and the minimum width is what the elements report, 0 for a text. Components that implement `ILayoutMeasurable` (TextBlock and Img do when this package is present) avoid both
- `LayoutRootBridge`: adapter for a root that sits inside a UGUI layout group or ScrollRect content. It reports the root's Fit size as an `ILayoutElement` (computed purely, no commit) and re-lays the tree out when UGUI resizes the root, so the content is right in the same frame. Each UGUI query is a full compute, so a bridged root costs three computes per UGUI rebuild
- `LayoutSystem`: `MarkDirty` and `ForceLayout`. Marked nodes are resolved to their roots and laid out on `Canvas.preWillRenderCanvases`, in both edit and play mode, ahead of UGUI's own rebuild so the graphics a commit resizes rebuild in the same frame. Roots are laid out outer first, and a pass that dirties a nested root (one under a plain rect it resized) is followed by that root's pass in the same flush. Static state is reset on every play mode transition with `[AutoStaticsCleanup]`, and the dirty set is keyed on managed reference identity, since an Undo resurrects a destroyed node with its old instance ID
- Property Bindings integration, present when `com.timbojimbo.propertybindings` is installed: `LayoutNodeProperties` descriptors (Offset, FloatOffset, Padding, Gap, AspectRatio, Width and Height values, Direction, AlignX, AlignY, AlignSelf) and a `LayoutNodePropertyBinding` that writes through the setters, so the Sequencer and Styling drive a node exactly as code does. A Unity Animation clip, which writes fields directly, re-lays the tree out on its notification
- `Sizing` inspector drawer: the mode and only that mode's fields on one line
- Layout sample: a showcase scene with the sizing modes, alignment, shrink and wrap, floating, aspect ratio and a scrolling list, and buttons that add and remove rows, flip the sizing row's direction, change its gap and pulse a block's Offset
